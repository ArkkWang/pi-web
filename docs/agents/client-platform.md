# Mobile and browser behavior

## Mobile software keyboard (`hooks/useViewportHeight.ts`)
- While an editor has focus and the visual viewport is more than `KEYBOARD_MIN_HEIGHT_PX` (60px) shorter than `innerHeight / scale`, the hook writes `visualViewport.height` to `--app-viewport-height`; smaller shrinks are Safari toolbars. Always compare against that zoom-corrected height, or iOS auto-zoom and pinch zoom leave the composer behind the keyboard.
- WebKit settles the shrunken height only after the keyboard animation, often without another `resize` (bugs.webkit.org 265578), and an IME candidate bar resizes the keyboard with no viewport event at all. So every trigger, composition/input/keyup events on a focused editor included, starts one non-restarting chain of re-reads (`SETTLE_DELAYS_MS`). Reading once per event keeps the full-screen height, and `scrollTo(0, 0)` then fights the page scrolling to the caret: a jittering composer.
- The same check sets `<html data-keyboard-open>`. Under `(max-width: 640px), (pointer: coarse) and (max-height: 500px)` (phone landscape included; tablets keep their controls) CSS hides `.chat-input-controls` and `.extension-status-shelf` and drops the bottom safe-area padding the keyboard covers. `MobilePwaLayout.test.mjs` asserts each targeted class exists on its component, so a rename cannot leave a rule silently dead.

## Completion sound
- `hooks/useAudio.ts` stores the toggle in `localStorage` as `pi-sound-enabled` and reuses one `AudioContext`.
- Autoplay policy requires unlocking sound from a user gesture: `ChatInput` calls the unlock hook from interactive controls, and `ChatWindow` plays the tone from `onAgentEnd`.

## Mobile sidebar drawer swipe (`hooks/useSidebarSwipe.ts`)
- Wired in `AppShell` for the mobile drawer only (`isMobile && !rightPanelOpen`; the file panel covers the phone screen): a right swipe from the left edge opens it, a left swipe on the open drawer closes it. The drawer follows the finger and the CSS transition finishes the move from wherever the finger left it. On desktop the hook is disabled and the split sidebar keeps its layout with no inline transform.
- The gesture starts inside a band, not at the very edge: from `DRAWER_SWIPE_BAND_START_PX` (36) to `drawerSwipeBandEnd()` — half the viewport width, floored at 140 and capped at 260. Android's back gesture owns the outer strip (`config_backGestureInset`, 30dp on the Jelly Star, `navigation_mode=2`) and no page can exclude it: a swipe starting there leaves the WebView (Native Alpha) instead of opening the drawer. CSS pixels are dp in this viewport, so the start constant clears the inset at any display density; the end follows the viewport because a fixed band would cover a different share of each phone. The right half keeps its own gestures. `useSidebarSwipe.test.mjs` asserts both the 30dp clearance and the bounds.
- Because the band reaches over content, a touch that owns its own gesture keeps it (`blocksDrawerSwipe`): an element that actually scrolls sideways (markdown tables, KaTeX display, mermaid, file previews), a form control, an active selection, or a touch held past `LONG_PRESS_MS` (500) before it moves. Code blocks are unaffected: they are `overflow: hidden` and wrap instead of panning.
- The container's `touchstart` is passive, so the commit to the horizontal axis happens on a `window` `touchmove` registered non-passive: only then can `preventDefault` stop the list behind the drawer from scrolling. A mostly vertical move (or a second finger) drops the gesture and leaves the scroll alone.
- On release the state is committed through `flushSync` *before* the inline `transform`/`opacity` are cleared. Without that order React has not rendered the target class yet, the transition starts from the pre-drag position, and the drawer jumps.
- Only `transform` is transitioned on the mobile drawer, and the backdrop's opacity/pointer-events live in the `is-open` class rather than inline styles so a drag can write its own opacity per move. A `box-shadow` in that transition list is re-rasterized every frame: measured over one open+close pair (production build, 6x CPU throttle), dropping it took main-thread time from 480ms to 201ms and style recalcs from 85 to 19, while `will-change: transform` changed nothing.
