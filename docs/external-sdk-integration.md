# 外部 SDK 会话接入：验证与工程复盘

## 当前边界

```text
子 Agent 工具 ──→ 同一个 Pi SDK 实例 ←── WebUI
                         │
                    各自订阅 SDK 事件
```

接口仅为 `register({ session }) → { release(): Promise<void> }`。没有插件提供的运行查询、发送或停止回调；WebUI 使用原来的 SDK 操作路径。注册者在自身任务收束后 `await release()`，再 dispose。release 等待 WebUI 已受理的准备/执行完成，拒绝新执行请求，但保留查询与显式停止，不冒充取消。

插件负责父子关系、工具侧受理限制、结果与通知；WebUI 操作不经过这些工具侧门禁。轮次表示连续执行区间，不保证每条 UI 输入独占一轮。插件不清空或补投共享队列来“修复”SDK；只有明确的工具 Stop 会清队列。完整接口和暂不开放的身份/文件变更操作见 [BRIDGE-CONTRACT.md](../BRIDGE-CONTRACT.md)。

## 本机验证

环境：Windows / Git Bash，Node 22.23.2，Pi SDK 1.0.0，隔离 Chromium。使用临时 agent 目录、随机 loopback 端口及本地 HTTP 模型替身；验证真实 SDK 和页面链路，而非某个真实模型的生成质量。没有替换原 30141 服务，测试后它仍返回正常的认证响应；测试进程和临时配置已清理。

- 插件回归 **28/28**：包括真实 SDK 跨仓库测试、外部直接执行的轮次/通知、混合图片队列不被插件清除、停止/关闭边界。
- 反向依赖检查：WebUI 发送、停止、压缩时，把插件 manager 的 send/stop 替换成抛错函数，操作仍成功；证明 WebUI 不再调用它们。
- 生命周期检查：阻塞 Web 输入准备，此时 SDK 仍 idle；关闭插件不得提前 dispose 或释放注册。放行后等已受理执行收束，才完成解除和销毁。
- 浏览器端到端：不刷新页面发现新子会话；运行显示 Stop、完成回 idle；follow-up 直接进入 SDK；续发和 Stop 正常；手动压缩显示并退出“压缩中”；无浏览器运行时错误。
- 性能抽样：带扩展的温热资源加载中位数约 **2.76 → 2.37 ms**；1 MiB 输出下 10000 次状态查询/序列化约 **20.72 → 18.78 ms**。只是本机短样本，不能认定性能提升，也不是完整冷启动或推理耗时。
- WebUI 直接相关回归 **92/92**；最后取消命令 guard 调整后，再跑核心受影响用例 **25/25**，类型检查和全仓库 lint 通过。
- 同环境全量对照：上游 v0.10.0 已观察 **1292 pass / 121 fail**，当前版本 **1300 pass / 121 fail**；121 个失败名称全部一致，已执行部分未观察到新增失败。两轮均在 180 秒超时，没有最终汇总，共同残留用例为 `mcp-read-only-policy.integration.test.mjs`，不能宣称全套通过。失败分类为 79 项 I18n、29 项 assertion、5 项 EPERM、7 项 EBUSY 和 1 项文件失败包装。全量对照早于最后取消命令 guard 小改，该改动由上述最终定向回归覆盖。详细原始报告在本机 `test-results/full-regression/REPORT.md`。

复现：

```bash
# home-scripts/pi/custom-tools/subagent 目录
PI_SDK_ENTRY=/absolute/path/to/pi/dist/index.js PI_WEB_ROOT=/absolute/path/to/pi-web npm test

# pi-web 目录：需要 sibling home-scripts 或设置 HOME_SCRIPTS_SUBAGENT
node e2e/external-sessions.mjs
# 已有 Chromium 可通过 E2E_CHROMIUM_PATH 指定；默认用 Playwright 管理的浏览器。
```

未覆盖：macOS/Linux 实机、真实模型服务质量、跨进程会话接管。SDK 准备阶段的通用可取消性、最终队列边界不由这个接口重新实现；不声称所有提交都能由 SDK 运行事件完整观察。

## 出现的问题及后续规避

### 1. 先保留两边的包装逻辑，后考虑真正的公共基础

初版为了完整保留插件的派发语义，让 WebUI 反向调用插件的 send/stop/isRunning。虽然能工作，却把界面绑定到特定管理器，偏离了“共享 SDK 实例”的目标。

**以后先做**：列明 SDK 已负责什么、插件业务是什么、谁持有哪个实例；画出一条实际发送和完成路径。先确认“共享实例”还是“远程执行器”，再写接口。已有业务策略不应自动扩展为所有入口都必须遵守的全局规则。

### 2. 把 SDK 运行事件误当作完整提交生命周期

输入处理、认证和启动前错误可能发生在 agent_start 之前。单看 isIdle 会误判可以释放；反过来，用插件私有状态填满这些缺口又会增加耦合。

**以后先测**：准备中、运行中、运行收束、释放四个边界。提交 Promise 由发起方负责；观察者只陈述可观察事实。释放必须等所有已知持有者收束，且允许用户继续发 Stop，不用假 idle 掩盖未结束的操作。

### 3. 单调用方的队列恢复逻辑不能直接带入共享实例

插件原先取出 SDK 队列再补投纯文本。在共享实例后，队列可能包含 WebUI 的图片和 follow-up，自动恢复反而会改写别人的输入。

**以后先守住**：共享资源只有一个权威实现。包装层使用 SDK 原生 prompt/streamingBehavior；观察路径不得隐式清队列、重试或再发请求。测试混合入口与非文本输入，而不只测试单入口成功。

### 4. 测试应该优先推翻架构假设，而不只是证明适配代码能跑

旧的 mock 缺少 SDK 的真实 settled/preflight 行为。浏览器压缩测试最初又因上下文过少被 SDK 正常拒绝——这是测试夹具不足，不能修改生产逻辑让它通过。

**以后先建立**：真实 SDK + 可控本地模型替身的最小测试；再做单测和浏览器验证。针对“无反向依赖”，直接让不应被调用的方法抛错；针对状态显示，必须看到状态开始和结束，而非只验证 HTTP 成功。

### 5. 扩大验证前缺少同环境上游基线

Windows 下全量测试存在路径、权限和清理失败。没有基线时，既不能把它们都归咎于改动，也不能称为上游既有问题。

**以后先记录**：同版本、同依赖、同平台的基线；按失败用例名称和原因比较新增失败。分别报告定向回归、全量回归、平台覆盖和超时范围。临时源码应放在项目编译扫描范围之外：本次把基线 worktree 放在 test-results 下，曾使其 demo 类型桩进入当前项目的 TypeScript 扫描；清理后类型检查通过，不应为测试目录污染去修改产品代码。

### 6. 并行实现应晚于边界确认

在共享 SDK 的责任边界尚未固定时，同时修改两边、测试和文档，导致三回调方案和后续调整都有返工。

**以后采用**：先以最小真实 SDK 实验确定契约，再按文件边界并行；接口变化时统一同步、冻结源码后验收。事先约定停止条件：目标链路和必要安全边界通过后，对基线同样失败的问题记录限制，不继续扩大修复。本次收口偏慢，后期有不断补边界、扩大验证的倾向，应以完成依据控制范围，而非追求把整个上游测试集修绿。保留隔离环境、不触碰正式服务是本次有效做法，应继续保持。
